# tele v1.2.2

This corrective release restores a stable, upgrade-safe macOS distribution
identity and bounds native Keychain access after the v1.2.0 and v1.2.1 ad-hoc
release signatures could trigger repeated authorization dialogs across binary
upgrades.

- macOS archives are now signed with Developer ID Application identity
  `J3S8HNBXSU`, hardened runtime, a stable `com.ardasevinc.tele` requirement,
  and an Apple notarization ticket
- new `keychain-v1` items bind both application access and ACL ownership to the
  pinned official signing requirement, preserving read, update, and purge
  authority across changed paths and binary hashes without granting it to
  arbitrary processes under the same user account
- unsigned, ad-hoc, source, and `go install` macOS builds fail before production
  Keychain access and remain supported through portable `vault-v1`
- Keychain diagnostics are metadata-only, successful reads are reused within a
  command, and the first authorization failure stops dependent reads instead of
  amplifying a single denial into many prompts
- macOS updater candidates must satisfy the pinned Developer ID and online
  notarization policy before replacement; macOS `go install` updates are
  deliberately check-only
- release construction now separates reproducible unsigned inputs from final
  signed bytes, with exact-byte GitHub attestations and Homebrew preservation

Users with a Keychain-backed v1.2.0 or v1.2.1 profile should use the exact old
binary that can still read that profile to migrate it to `vault-v1` before
upgrading. Retain the old Keychain instance and migration receipt. The official
v1.2.2 binary can then initialize a fresh `keychain-v1` instance and migrate the
verified vault into it. Repeatedly approving legacy access dialogs or deleting
old items is not a safe migration procedure.

The portable vault format, Linux `vault-v1` and `secret-service-v1` support,
Telegram command contracts, and `tele/v1` machine-output schemas remain
compatible.
